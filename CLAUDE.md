# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single self-contained static website for "Nuzzle," a fictional remote pet-sitting company: a live camera plus a proprietary AI companion robot ("NuzzlePal") for cats and dogs, with more species planned. The whole site — markup, CSS, and JavaScript — lives in one file: `index.html`, plus a flat `images/` folder of photos it references by relative path. There is no build step, no package manager, and no dependencies to install. See [README.md](README.md) for the full feature list and image credits.

## Running it

Open `index.html` directly in a browser, or serve the folder (`python3 -m http.server`) to sanity-check relative image paths. There is no dev server, bundler, linter, or test suite configured in this repo. The repo is also public on GitHub (`ElroyQQ/nuzzle_pet_care_POC`) with GitHub Pages enabled, live at https://elroyqq.github.io/nuzzle_pet_care_POC/ — Pages serves whatever is on `main`, so a push there updates the live site with no separate deploy step.

## Architecture

Everything is inline in `index.html`:

1. **`<style>`** — CSS custom properties on `:root` (`--paper`, `--card`, `--ink-900`, `--brand-500` for the general CTA/glow color, plus one token per wheel category: `--cat-500`, `--dog-500`, `--future-500`, `--bonus-500`). See "Design system" below before touching colors, fonts, radii, or shadows — it explains why `--ink-900` is text-only now and what replaced it for solid-block backgrounds.
2. **Markup** — header/nav, hero, stats bar, feature grid, services grid (cats/dogs/future pets), the NuzzlePal device section, how-it-works steps, an app-preview phone mockup, a spinnable plans wheel, testimonials, FAQ, closing CTA, footer. Three fixed roaming mascot buttons (`#roamBot`, `#roamDog`, `#roamCat`) sit outside `<main>`, right before the closing `</body>`.
3. **`<script>`** — a single IIFE, no external JS libraries. `SERVICES`, `PET_PLANS` (keyed `cat`/`dog`/`future` — deliberately no `bonus` key), `WHEEL_ORDER` (`['cat','dog','future','bonus']`), `TESTIMONIALS`, `FAQ`, `PET_MODES`, `ROAM_LINES`, and `CHASE_LINES` are the data to edit for copy changes. `renderServices`/`renderPlanPanel`/`renderTestimonials`/`renderFaq` build their sections from that data; `renderBonusPanel` builds the voucher panel separately, and `renderActivePanel(petKey)` dispatches between the two. `selectPet(petKey, extraTurns)` is the shared handler behind the plans wheel, its SPIN button, and its tab buttons — it does the rotation math (see below) and calls `renderActivePanel` after the spin animation. `initRoamBot()`/`initRoamCritter()` drive the roaming mascots (see below). `setPetMode()` drives the Cat/Dog toggle on the NuzzlePal illustration (swaps accessory, ring-light color, caption). `setPhoneTab()` drives the Live/Talk/Insights app mockup. Nothing submits anywhere — "Choose plan," "Join the Waitlist," "Copy code," and the bundle-note link just show a toast (or use the Clipboard API), consistent with this being a demo/portfolio site with no backend.

## The plans wheel

`#wheel` is a plain circular `<div>` colored with a CSS `conic-gradient` (four 90° wedges: cat=`--brand-500`, dog=`--dog-500`, future=`--future-500`, bonus=`--bonus-500`) — there is no SVG arc math. `selectPet()` keeps a running `wheelRotation` value (in degrees, can exceed 360) and always rotates *forward* to whatever multiple of 360 lands the target wedge's center under the fixed pointer at the top, so repeated selections never spin backwards. `initWheel()`'s click handler converts a click's pixel position into a compass angle with `Math.atan2`, compensates for the wheel's current rotation, and figures out which wedge was actually clicked — the math is generic over `WHEEL_ORDER.length`, so it didn't need to change when the Bonus wedge was added; only the four `conic-gradient` stops and the four `.wheel-label` elements' `--ang` values (45/135/225/315deg, i.e. `index*90 + 45`) needed updating. On page load, `initWheel()` snaps the wheel to the default active pet's position with `transition:none` first, so the wheel doesn't visibly spin on first paint.

**`#wheel` itself carries no border or box-shadow** — the border lives on its parent, `.wheel-frame` (a plain non-rotating wrapper); `.wheel-frame` has no box-shadow either, on request (the wheel reads as a flat disc, not a "sticker" like the site's cards/buttons). `#wheel` is the only element with the `transform:rotate()` on it; `box-shadow` is painted as part of an element's own rendered box and rotates rigidly along with any `transform` on that same element, so a hard (non-blurred) offset shadow directly on the rotating wheel would visibly swing to a different side of the circle depending on the current cumulative rotation — it looked like an uneven black "bulge" on whichever wedge happened to be nearest that rotated shadow direction. If a shadow is ever wanted back on the wheel, put it on `.wheel-frame`, never on `#wheel`.

The **Bonus** wedge doesn't map to a `PET_PLANS` entry — `selectPet()`'s validity check is `WHEEL_ORDER.indexOf(petKey) !== -1`, not a `PET_PLANS` lookup, specifically so `bonus` is a legal wheel value with no plan behind it. `renderBonusPanel()` lazily creates a `{code, issued, expires}` object on first view (`bonusVoucher`, module-level, generated once and reused — clicking away and back shows the same code rather than re-rolling it) using `generatePromoCode()` (excludes visually ambiguous characters like `0/O`, `1/I`) and `addOneMonth()` (uses `Date#setMonth`, which correctly rolls over year/day-count edge cases). If you change the voucher's validity window, edit `addOneMonth` — don't hardcode "30 days," since the copy explicitly says "1 month."

## Roaming mascots

`randomViewportSpot(el)` and `hopMascotTo(el, x, y)` are shared by all three mascots: pick a random point within the viewport (16px margin, sized off the element's own `offsetWidth`) and move the button there via inline `left`/`top` (clearing the CSS `right`/`bottom` defaults first), replaying the `bot-hop` keyframe. `initRoamBot()` wires the robot's own click to that plus a `ROAM_LINES` bubble. `initRoamCritter(id, kind)` wires `#roamDog`/`#roamCat`: on click, the critter hops, then `chaseWithBot(spot, kind)` fires — after a ~450ms delay (so it visibly reads as the robot *reacting*, not moving in lockstep) it hops the robot to a random point offset ~80px from the critter's new spot and shows a `CHASE_LINES[kind]` bubble. If you add a fourth roaming mascot, reuse these two primitives rather than duplicating the hop logic again.

`#roamDog`/`#roamCat` are **face-only** icons (`viewBox="0 0 80 80"`, no body/feet/tail) — this went through two revisions. The first pass had a full body (head + feet + tail + collar), which read as a same-shaped colored blob at the actual 40–52px render size; a second pass added more detail (tail, collar), which made it *worse* — more competing thin shapes at that size, not more legible. What actually fixed it was researching real flat dog/cat emoji-style icon conventions and matching that formula instead of inventing one: **dog** = big floppy ears + a light (white) muzzle patch + dark nose + tongue, no collar; **cat** = tall pointed ears with a pale pink inner-ear triangle + whiskers + small nose/mouth, no tail. The muzzle patch and whiskers respectively are the actual species signal at small sizes — ear shape alone reads as "fold" vs "point" but is subtle; the whisker lines / white-muzzle-with-black-nose are unambiguous even at 40px. If asked to touch these again, don't add detail (tails, collars, body) — that's the direction that already failed twice; if legibility is still an issue, look at increasing size or contrast instead.

## Design system

The site is now an **"editorial spec-sheet" look** — warm near-white paper, huge condensed all-caps Bebas Neue poster type, and real pet/device photography carrying the page instead of glow, gradient, blur, or glassmorphism. This is the fourth visual pass: soft-rounded/pastel (original) → neo-brutalist (flat colors, thick black borders, hard offset shadows) → dark-cosmic "Orbital AI" (near-black void, violet glow-arc motif, starfield) → this one, which was an explicit, deliberate reversal of the dark-cosmic pass specifically because that pass (and its predecessors) still read as generic "AI-SaaS template" chrome regardless of palette. If you're reading an old commit, grep for `Archivo Black`/`border-radius:0` (brutalist), `#FFF3D6`/`#0B0B0B` as a page background (original), or `#06040F`/`Orbital AI` (dark-cosmic) to orient yourself — none of those describe the current site.

**Full token reference, component-by-component rules, and Do's/Don'ts now live in [DESIGN.md](DESIGN.md)** (with a machine-readable sidecar at `.impeccable/design.json`) — written by the project's own documenter at the end of this redesign, generated from the shipped code rather than from intentions. Treat DESIGN.md as the source of truth for colors, type scale, spacing, and component rules going forward; the summary below is just enough to orient a session that hasn't opened it yet.

**Quick orientation**: `--paper:#E7E6E5` / `--ink-900:#0B0B0A` are the base; `--card:#DCDAD8` / `--card-2:#CFCDC9` step the surfaces. Bebas Neue is the *only* heading face at every scale (`line-height:.96`, all-caps); Manrope carries body/nav/buttons; Space Mono marks anything that reads as data (timestamps, stats, photo-caption chips, the NuzzlePal photo's rotated spec labels). Species colors (`--cat-500:#B23E6B`, `--dog-500:#2E5AA8`, `--future-500:#3D7A5C`, `--bonus-500:#A87C2E`) are confined to small flat pill/tag/active-state fills — never a background, gradient, or glow (DESIGN.md calls this the **Muted-Tag-Only Rule**). Buttons are flat small-radius solid `--ink-900` fills with white text — no pill shape, no gradient, no glow shadow (the **No-Glow Rule**: zero `blur()`/`backdrop-filter`/colored glow anywhere in the shipped CSS, confirmed by grep). Every icon on the page — nav, feature grid, plan tabs, wheel labels, and the plan-card checklist tick — is a drawn `stroke-width:1.7`-ish line icon (inline SVG or CSS `mask`), never a Unicode glyph or emoji (the build's one remaining "✓" glyph was replaced with a CSS-mask SVG during the finish-review pass).

Like every prior pass, this was done under the same **pure CSS + inline-SVG-recolor discipline**: zero changes to any element's `id`, class name, or `data-*` attribute. One documented, explicitly user-approved exception this pass: a handful of small, well-commented `<script>` changes that fold in interaction fixes from a design critique alongside the visual rewrite (demoting the plans wheel out of the primary purchasing path, removing the forced ~1.5s wheel-spin delay on direct plan-tab clicks so a confident pick swaps near-instantly, keeping the roaming mascots clear of the hero on mobile, and morphing the hamburger icon into an X on open) — see `.impeccable/surfaces/index-html.md`'s Direction contract for the record of that scope decision. Everything else (emoji → inline-SVG icon lookup, the checkmark fix, the plan-tabs' Bonus button removal, the stats-bar restyle, the `--ink-500` contrast fix) is markup/CSS only, zero script-logic change.

**Two follow-up fixes from the finish review**, worth knowing if you're touching these areas again: `--ink-500` shipped initially at `#7A776F` (3.59:1 against `--paper` — fails WCAG AA) and was darkened to `#615F58` (4.5:1+ against both `--paper` and `--card`) before this pass was called done; and `#planTabs` (the primary Cats/Dogs/Future-Pets plan picker) no longer lists a fourth "Bonus" button — Bonus stays reachable only through the demoted "Feeling lucky?" wheel widget below, so the primary purchasing path never mixes a real plan with a gambling-flavored wedge. `WHEEL_ORDER` (script) still includes `bonus` and the wheel itself still has all four wedges; only the static tab markup changed.

Text-on-bright-background contrast still needs a manual check per component: white text on the species colors and `--ink-900` fills (all saturated-to-near-black, high contrast by construction); `--ink-500`/`--ink-700` secondary text needs a real contrast check against whichever of `--paper`/`--card`/`--card-2` it sits on rather than assumed from one surface, per the fix above.

## Image & video policy

Every photo and video on this site must be real, freely-licensed footage — never an illustration, drawing, or AI-generated image/video. Source from Pexels (Pexels License) or another clearly free/CC0 source, and record credits in the footer of `index.html` and in [README.md](README.md#image-credits) when adding new sourced images or video.

The hero's "LIVE · NUZZLEPAL CAM" background (`video/nuzzlepal-cam-loop.mp4`) is real Pexels footage of a dog walking through a home at floor level, chosen specifically to read as a pet-height camera following the animal around — not a generated or staged "robot POV" shot. If this is swapped, keep sourcing from real footage with a similar low, following angle rather than a generic dog video, or the "NuzzlePal is watching" framing stops making sense.

**The "Meet NuzzlePal" hero image is now a real photo**, `images/nuzzlepal-device.jpg` — a small two-wheeled home companion robot (Pexels, Kindel Media, see README credits), cropped and lightly contrast/color-adjusted with Pillow (crop only — no compositing, no background removal), not generated. NuzzlePal is fictional, so no photo of it specifically exists; the same approach as the Dodo Burgers dodo mascot applies — find a real photo of a close analog and use it as-is (with ordinary photo-editing, not illustration) rather than drawing a fictional one. It's meant to read as pet-sized (cat/small-dog scale), evoking real consumer home robots (Roomba-style vacuums, small companion bots) — if this photo is ever replaced, keep that same scale impression and keep sourcing a real photo, not an illustration or render.

**Two remaining exceptions**, both flat single-color iconographic work, not photorealistic subject illustration:
1. `#deviceSvg`, a *thin transparent SVG overlay* sitting on top of the device photo (see `.device-overlay` in CSS), carries the parts of that section JS needs to manipulate: `#ringLight` (the glow ring around the camera lens — its `viewBox="0 0 640 815"` is sized to exactly match `images/nuzzlepal-device.jpg`'s pixel dimensions, and `cx`/`cy` were measured from the actual lens position in that photo, so a different photo would need these re-measured) and `#accCat`/`#accDog` (small floating callout graphics — a laser-dot beam, a treat-launcher badge — positioned near the robot rather than attached to it, since they're UI annotations on a real photo, not literal hardware). The three roaming mascots (`#roamBot`, `#roamDog`, `#roamCat`) are separate, fully illustrated SVGs (not photo overlays) — small, flat, UI-icon-scale mascots stylized to match the robot photo's role, using the same magenta/blue accent colors as the cat/dog wheel wedges and service tags.
2. The pet-themed background decoration — the repeating paw-print pattern on `body::before` and the large dog/cat silhouette watermarks (`.critter-deco` in `#why` and `.testimonials`) — was added on explicit request to make the site feel more "pet themed," using CC0-licensed flat SVG icons from SVG Repo (see README credits). Currently recolored to a soft lavender (`#B49CDB`, pulled from the Orbital-AI reference palette) at low opacity (`fill-opacity` ~0.05 in the inline SVGs, `opacity:.1` on `.critter-deco`) so they read as a faint violet glow on the dark background rather than the flat black they were in the earlier light/brutalist passes. `body::before` also layers in a handful of `radial-gradient` point-stars alongside the repeating paw pattern, for the reference's starfield texture — both live in the same `background-image` stack (comma-separated gradient layers, then the paw-pattern `url(...)` last), so if you add or remove a star layer, keep `background-size`/`background-repeat`'s comma-separated lists the same length and order as the `background-image` list, or they'll pair up with the wrong layer. Source files also live at `images/deco/*.svg` for reference.

Don't treat either exception as license to introduce photorealistic illustrations elsewhere — hero, service cards, testimonials, the NuzzlePal photo, etc. should stay real photos. If asked to add more decorative background art or mascots, keep it in the same family (flat, low-opacity or small-scale, CC0-sourced or hand-built, recolored to the brand palette) rather than introducing a different illustration style.

## Content notes

- The FAQ item "How smart is the AI, really?" is intentionally direct: NuzzlePal's models are described as trained on publicly available pet-behavior footage and other public internet data, then fine-tuned per-pet with owner consent — and explicitly *not* a substitute for veterinary care or an in-person sitter. Keep this framing if the FAQ is edited; it was a deliberate choice to be upfront rather than vague marketing-speak about "proprietary AI."
- Pricing, stats (e.g. "11,400+ homes"), and testimonials are illustrative placeholder content for a demo site, not real figures.
- All three roaming mascots (`#roamBot`, `#roamDog`, `#roamCat`) are `position:fixed` and move within the viewport only (not the full scrollable document) — this was a deliberate simplification so none of them can wander somewhere the visitor has to scroll to find, which read as broken rather than playful during testing.
- Pricing/stats/testimonial placeholder-content note above also covers the voucher: the promo code and dates are real, freshly computed values (not hardcoded strings), but the "10% off" discount itself isn't wired to anything — there's no cart or checkout on this site for it to apply to.
